Lesson 10 · Coding agents

Direct an agent without giving up engineering control

Supply the right context, constrain tools, inspect the work, and require evidence. Treat the agent as a fast collaborator, not an authority.

  • About 50 minutes
  • Prerequisite: Lesson 9
  • Focus: judgment and safety
The problem

An agent produces 800 lines in one minute and says the feature is complete. What, exactly, should you trust?

Why it matters: Fluent text and plausible code are not proof. Trust comes from a bounded request, visible source changes, independent review, and checks against real behavior.

01

Understand what an agent can and cannot know

The mystery

If a coding agent can read the repository and run tests, why does it still need direction?

The answer: Tools supply observations, not product authority. The agent may not know the user's real priority, an unwritten business decision, or whether a risky action is acceptable. It must inspect, ask when needed, and report uncertainty.

A coding agent is software that can reason about a task and use tools such as file search, editing, a terminal, or a browser. Different agents have different capabilities and permission systems.

The agent canThe agent must not assume
Search source, read documents, compare diffs, and run allowed checks.That an old document, a common framework pattern, or a familiar error is correct here.
Propose a design, implement an approved change, and explain evidence.That its preferred library, architecture, or naming convention overrides this repository.
Ask for a missing decision and stop at a safety boundary.That “make it work” permits data loss, secret access, a commit, a push, or a larger scope.

You remain responsible for product decisions and risky approvals. The agent remains responsible for following instructions, inspecting before editing, and giving an accurate account of what it did and could not verify.

02

Write a task brief with a finish line

Problem to solve

Why does “improve the app” produce unfocused work even when the agent is capable?

The answer: The request has no observable finish line or boundary. A good brief defines the outcome, context, constraints, and required proof.

Use five parts:

  1. Outcome: The user behavior or engineering result you need.
  2. Context: Relevant current behavior and documents, not a dump of every file.
  3. Boundaries: What to preserve, exclude, or ask about before acting.
  4. Deliverable: Code, diagnosis, plan, review, or documentation. A question does not automatically authorize code changes.
  5. Done means: The real workflow and project commands that must pass.
Example brief for an existing requirement
Outcome: Verify the saved theme behavior; do not change the product.
Context: Read docs/spec.md and frontend/src/theme.tsx.
Scope: Inspect startup fallback, save timeout, retry, and browser tests.
Boundaries: Read-only. Do not access local configuration secrets.
Deliverable: Report confirmed behavior and any coverage gaps with file paths.
Done means: Every claim is tied to source or an executed check.
Weak brief versus useful addition
Weak:   Fix Pipeline.
Useful: Reproduce the reported drop-position bug against docs/spec.md.
        Preserve stage probability rules and keyboard movement.
        Add a regression check only if the diagnosis confirms the cause.
        Run the focused test, then npm run check before reporting.

If the request is ambiguous in a way that changes the next action, ask a focused question. Do not interrupt for trivial naming or formatting choices that repository conventions already answer.

03

Load the minimum reliable context

Design puzzle

Would reading every file make an agent safer, or can irrelevant instructions and old change folders create confusion?

The answer: Relevant, current context is better than maximum context. Read the governing documents and the code on the actual path. Exclude other changes and generated output.

Accountable's context order is clear:

  1. Read AGENTS.md for navigation, change-folder rules, and required checks.
  2. Read docs/spec.md for current product behavior.
  3. Read docs/Standers.md and docs/TECH_STACK.md for implementation constraints.
  4. Read only docs/changes/<current-branch>/ for the current intent and plan.
  5. Inspect nearby source, imports, manifests, lockfiles, and existing tests before choosing an approach.

A skill is reusable agent guidance for a kind of task. This project has a brand skill at .agents/skills/brand/SKILL.md. A UI task should use it rather than reconstructing colors and tone from memory. A skill guides development; it is not imported by the CRM.

Local instructions can be nested: Check for a more specific AGENTS.md when working in a subdirectory. If documented practice changes, update the applicable guidance instead of leaving contradictory instructions.

Long sessions and compacted context

An agent may receive a summary after a long session. Treat it as a record of conclusions, not live tool state. Recheck background tasks, working-tree state, and current files when needed. Do not repeat finished work or ask again for information already supplied.

04

Use an evidence-based implementation loop

The problem

An agent edits first and investigates later. Why does that often create broad, hard-to-review changes?

The answer: Without a current code map, the agent guesses at ownership and conventions. A short discovery step prevents unnecessary files, duplicate utilities, and incorrect fixes.

  1. Inspect
  2. Plan
  3. Edit
  4. Verify
  5. Review
StepGood practice in this repository
InspectCheck git status, preserve existing work, read the actual implementation, and reproduce reported failures.
PlanUse existing seams such as data.tsx, API routes, shared services, and Store. Avoid premature abstraction.
EditMatch naming and structure. Use small functions. Delete dead code instead of commenting it out. Keep comments focused on why.
VerifyRun focused tests during work. Exercise the real user path, not only imports or compilation.
ReviewInspect the final diff, remove generated artifacts, check documentation, then run npm run check.

Do not assume a library exists because it is popular. Confirm it in the manifests and lockfile. Do not silently add a dependency for a capability the project does not have; explain the gap and choose with the user when it changes the design.

For a bug, find the cause before naming it. For an explanation, answer from evidence without changing files. For an action request, carry the work through verification instead of stopping at a suggestion.

05

Choose tools by job and privilege

Design puzzle

An agent can use a shell command for everything. Why prefer dedicated read, search, edit, and browser tools?

The answer: Focused tools make intent visible and can enforce path and permission boundaries. Shell commands are necessary for processes and test runners, but they can hide broad effects.

Use the least powerful tool that can do the job reliably:

  • Search tools to find unknown files or content.
  • Direct file reads for known paths, with pagination for large files.
  • Exact edits for existing source and clear writes for new or complete files.
  • A shell for builds, tests, Git inspection, and process coordination.
  • Browser automation for real rendering, interaction, console, and screenshots.

MCP is a tool connection, not product AI

Model Context Protocol (MCP) gives an agent a standard way to discover and call external tools. Accountable configures Playwright MCP in .mcp.json and .codex/config.toml. It can inspect the running app and save screenshots in .playwright-mcp/.

The CRM does not require MCP. Playwright Test in e2e/ is the repeatable automated suite; Playwright MCP supports interactive inspection. An npx ...@latest MCP launch may need network access even though the installed application runs offline.

Specialist agents need narrow scopes

The configured reviewer is read-only and reviews a stated branch range against the policy. The configured ui-check agent inspects the running app in both themes, avoids sales writes, restores the original theme, and reports screenshots and coverage gaps.

Use a specialist when the user or project workflow authorizes it. Give it the exact goal, known paths, and scope. Do not delegate your own understanding, duplicate its searches, or let it silently expand into implementation. A reviewer reports; the implementer decides how to address findings.

06

Use defense in depth for permissions and secrets

The problem

If one permission rule denies reading .env, is secret access impossible?

The answer: No. A rule may cover only one tool or a literal path. Computed shell paths and other tools can bypass a narrow gate. Safe behavior, scanning, user approval, and limited privileges must work together.

Defense in depth means several controls cover one another's gaps. This repository uses or documents:

ControlPurposeImportant limit
Permission rulesExamples allow npm test, ask before git push, and deny a direct .env read.Patterns differ by agent. Local settings may be ignored by Git and differ per developer.
Codex environment hook.codex/hooks/protect-env.mjs denies matching tool calls that name an environment file.It inspects tool arguments and can miss paths computed at run time.
GitleaksScans the working tree or staged changes and redacts detected values.No scanner proves that every kind of secret is absent.
Git ignore rulesKeep local dependencies, data, backups, and private settings out of normal source control.Ignored does not mean encrypted or safe to upload elsewhere.
Secret handling is behavioral: Do not read, copy, print, or transmit secret files through another tool to evade a denial. Never put real credentials or customer backups in prompts. Keep .env files unchanged; ask the project owner to make required changes.

Git and external effects

Local reads and reversible edits have a small blast radius. A reset, force-push, dependency publish, deployment, or push to a shared branch has a larger one. Inspect git status first. Do not commit, push, reset, rebase, or discard work unless the user asked for that action. A denied action is declined; do not route around it.

07

Review the agent's reasoning and evidence

Your challenge

The agent lists ten tests and says “all good.” What questions should you ask before accepting the result?

The answer: Ask what ran, what each check observed, what changed, what remains unverified, and whether the original user scenario still works.

A trustworthy completion report is specific:

  • Names the behavior changed and the main files involved.
  • Explains any material assumption or product choice.
  • Lists executed checks and their actual result, including coverage and browser runs when relevant.
  • States failures, skipped platforms, unavailable tools, and remaining gaps plainly.
  • Does not call a change complete while required checks are red or could not start.
  • Does not hide unrelated failures; it identifies them instead of fixing them without scope.

Inspect git diff yourself. Look for scope creep, unrelated formatting, generated files, stale comments, secret values, weakened assertions, and undocumented behavior. A smaller correct change is better than a large impressive one.

Useful follow-up prompts: “Show the exact evidence for that claim.” “Which requirement covers this extra file?” “What failure mode is still untested?” “Did the new regression test fail before the fix?” “What did you leave unchanged, and why?”
08

Check your understanding

1. Why is a detailed prompt not enough?

The implementation can still misunderstand code, introduce unrelated behavior, or report unrun checks. You must inspect the diff and verify real behavior.

2. What is the difference between Playwright MCP and Playwright Test?

MCP gives a coding agent interactive browser tools. Playwright Test is the repository's repeatable automated end-to-end suite. They support each other but are not interchangeable evidence.

3. Why are permission rules only one layer?

A rule may match only one tool or literal argument. Safe agent behavior, user approval, secret scanning, and review are still necessary.

4. Should a reviewer agent edit the defects it finds?

Not in this project's configured review role. It stays read-only and reports findings with location, trigger, and effect. This keeps implementation and independent inspection separate.
