Lesson 12 · Guided capstone

Connect product behavior to engineering evidence

Run Accountable, inspect real requests, exercise recovery and themes, direct a read-only agent, and decide whether the complete project check passes.

  • About 45 minutes

Your challenge

Can you explain what happened, prove it with the running system, and direct an agent without accepting “done” on faith?

01

Prepare and protect your data

Problem to solve

You want to experiment with deletion, movement, and themes. How can you learn through real actions without gambling with records you need?

The answer: Check the environment, save a full backup, and use clearly named sample records. Do not practice dataset replacement on needed data.

This lesson changes your local sample dataset through normal app actions. If your database contains records you need, save a full backup first.

  1. Open a terminal in the repository root.
  2. Check the installed tools:
node --version
uv --version
gitleaks version

Node.js must be 24 or later; Node.js 26 is the target. uv manages Python 3.12. Install Google Chrome for browser tests and Gitleaks 8.30 or later for the complete checks.

If you have not completed setup, run these commands with internet access:

uv python install 3.12
uv sync --locked
npm ci

Optional but recommended before data exercises:

npm run save

Write down the printed backup ID and path. The save command can run while the app is open because it uses a consistent writer transaction.

Do not practice load or reset on needed data: This lesson does not ask you to run npm run load or npm run seed. Both replace the full current sales dataset after an automatic backup.
02

Start both servers

Problem to solve

Why does the development script wait for /api/version before it starts Vite instead of showing the browser URL immediately?

The answer: When the URL appears, both the interface and its API can respond. A frontend-only ready state would be misleading.

npm run dev

Watch the terminal. Uvicorn starts first. The script waits for /api/version, then starts Vite. Open the printed local URL, normally http://127.0.0.1:5173.

Checkpoint: The Dashboard shows sales figures, charts, follow-ups, recent activity, and an embedded pipeline. Navigation opens Organizations, Contacts, Deals, Pipeline, Trash, and Data. A shared top bar shows the current Light or Dark choice.

Keep this terminal open. In a second terminal, you can run read-only commands or npm run save from the same repository root.

03

Inspect frontend and API traffic

Your investigation

Can you see the conversation behind the Dashboard instead of taking its figures on trust?

The answer: Chrome's Network panel exposes the actual API requests and JSON. Compare those values with the charts and totals on screen.

  1. In Chrome, press F12 and open Network. Choose Fetch/XHR.
  2. Reload the page. Select version, dashboard, and pipeline.
  3. Inspect each URL, method, status, and JSON response. Compare values with the visible panels.
  4. Select the theme request under preferences/theme. Identify its method and response.
  5. Open Sources and find src/main.tsx, src/theme.tsx, or another frontend module.
ObservationWhat it supports
/api/version returns dataset and revisionThe frontend can detect sales-data writes and whole-dataset replacement.
/api/dashboard contains months, totals, funnel, follow-ups, and recent activityThe backend calculates report data; React presents it.
Fonts and modules use the local originThe running app uses local assets rather than an external content network.
/api/preferences/theme returns light or darkThe preference is app data from the backend, not only browser storage.

Open Console and check for errors. You can try a harmless calculation; it changes no app data:

Browser console
const valueCents = 12500;
const probability = 25;
const expectedCents = valueCents * probability / 100;
console.log(expectedCents); // 3125
04

Create, inspect, delete, and restore a record

Your investigation

A record appears on screen. How can you prove it is saved—and then prove Trash is recovery, not permanent deletion?

The answer: Inspect the POST, refresh, delete through the impact dialog, and restore from Trash. Each step tests a different part of the persistence path.

  1. Open Organizations and select Add organization.
  2. Set Name to Learning Example and Industry to Education. Save.
  3. Search for learning. Search is case-insensitive.
  4. In Network, inspect the POST to /api/records/organizations. Look at the JSON body, X-Dataset header, and saved response.
  5. Refresh the browser. The organization remains because SQLite saved it.
  6. Select Delete for Learning Example. Read the impact dialog and confirm only if it has no blockers.
  7. Open Trash, find the organization, and select Restore.
  8. Return to Organizations and search for it again.
Checkpoint: You used a React form, JSON POST, backend validation, committed transaction, soft delete, and restore. Refresh did not clear the saved record.

If you linked contacts or deals to this organization, deletion behavior can differ. Read the dialog. Do not bypass a blocker for the exercise.

05

Follow a pipeline change

Your investigation

A card appears in a new column. Did anything else change, or was movement only visual?

The answer: Inspect probability, totals, timeline, and the move request. A stage change has business effects; a same-stage reorder changes position only.

Choose an identifiable open sample deal.

  1. Note its current stage and probability.
  2. Select Move. Choose a different open stage and a position. Submit.
  3. Observe the destination default probability and updated column totals.
  4. Open the deal and find exactly one new stage event in its timeline.
  5. In Network, inspect the POST body for /api/pipeline/move. Identify id, stage, before, and revision.
  6. Move it back if desired. The app records both transitions and applies each destination default.

Reorder a card within its current column. Its probability does not change and no stage event is created. Refresh to confirm the saved position.

Requirement trace: Find the corresponding rules in docs/spec.md under “Pipeline movement and ordering,” then the implementation in backend/services/sales.py and browser checks in e2e/sales.spec.ts.
06

Verify saved themes and keyboard access

Your investigation

Is Dark only a temporary CSS class in this browser tab, or is it a shared app preference?

The answer: Reload and open a fresh browser context or another browser on the same computer. The backend saved the preference, so the app can restore it.

  1. Use Tab to reach the Theme switch. Confirm visible keyboard focus.
  2. Press Space to select Dark. Inspect the PUT /api/preferences/theme request and response.
  3. Check a form, Pipeline, Dashboard charts, and status labels. Values must stay unchanged while surfaces and chart colors adapt.
  4. Reload. Confirm Dark remains. Return to Light or restore your original choice.
  5. If practical, open the app in a fresh browser context. Confirm it reads the saved mode.

Do not simulate a stalled request in your normal browser session. The isolated Playwright tests in e2e/theme.spec.ts cover startup and save deadlines, retry, stale responses, and reload reconciliation without risking your data.

07

Export a workbook and save a full backup

Problem to solve

You have an Excel export. Does it contain everything needed to restore Trash, notes, follow-ups, stage history, and board order?

The answer: No. Exchange and recovery have different contracts. A workbook contains three active main record types; a JSON backup contains complete sales and recovery state.

Workbook exchange

  1. Open Data.
  2. Select Download template and inspect the three sheet names in a spreadsheet program.
  3. Select Export workbook. Compare its IDs and rows with the app.

You do not need to import the file. Preview rolls back its trial changes. Apply commits only after validation and a matching token.

Complete sales backup

In a second terminal at the repository root, run:

npm run save

Record the new ID. Find the JSON file in data/backups/. You can read it, but do not modify it: the checksum would no longer match. Do not send it to an agent or public service if it contains real business data.

ArtifactContainsMain use
Workbook .xlsxActive organizations, contacts, and dealsSpreadsheet exchange
Backup .jsonSales records and all recovery stateFull local sales recovery
Database .dbLive SQLite tables and app preferenceNormal persistent operation
08

Direct a read-only coding agent

Your investigation

Can you get a useful agent result without allowing edits, secret access, or a vague “review everything” task?

The answer: Give a narrow read-only brief with sources, boundaries, and a required output. Then verify its claims against your own observations.

Give an agent this brief, or adapt it to your tool:

Read-only trace task
Outcome: Explain one stage-change requirement-to-test trace.
Read: docs/spec.md, docs/REVIEW.md, docs/Standers.md,
      backend/services/sales.py, backend/services/records.py,
      backend/tests/test_sales.py, and e2e/sales.spec.ts.
Scope: Stage probability, one stage event, and same-stage reorder only.
Boundaries: Do not edit files, run formatters, access environment files,
            change Git state, or inspect unrelated change folders.
Deliverable: A table linking each requirement to source and verification.
             Identify any claim you cannot confirm. Do not call this a
             full review or claim that tests ran unless you ran them.

Check the response:

  • Does every path exist and every claim match the named source?
  • Does it distinguish a stage change from a reorder?
  • Does it distinguish source inspection from executed test evidence?
  • Did it stay within the requested files and read-only boundary?
  • Can you connect its trace to the Network request and timeline you observed?

If your agent has a configured reviewer role, compare its read-only constraints with .codex/agents/reviewer.toml. Do not start a broad specialist review unless your workflow authorizes it.

09

Run complete verification

Your investigation

Can you show that source builds and all quality gates pass without using or resetting the data you just changed?

The answer: Stop the development servers, build the frontend, and run the full check. Test fixtures use isolated databases, backups, and ports.

Return to the app terminal and press Ctrl + C. Playwright will start its own isolated app.

npm run build
npm run check

The build checks TypeScript and writes frontend/dist/. The full check covers formatting, lint, frontend and backend types, secrets, Vitest, pytest, and Playwright. Every test suite runs even if an earlier suite fails. The final exit code must be 0 for a passing run.

Evidence to recordYour result
Operating system and tool versionsFill this in yourself.
Build resultPass, fail, or not run—with the actual command result.
Vitest and pytest totals and line coverageRecord actual values; each coverage threshold is 80%.
Playwright result in installed ChromeRecord actual total; a startup failure is not a pass.
Gitleaks and final exit statusRecord actual result, not an assumption.
Untested platforms or behaviorList gaps plainly.

The tests use temporary databases and backups. They do not reset Learning Example or your normal sample board changes. Check git status afterward and do not mistake generated output for source edits.

10

Troubleshoot common problems

Problem to solve

The app will not start. Is deleting the database a sensible first step?

The answer: No. Match the symptom to a tool or layer. Read errors and check dependencies, ports, readiness, and responses before considering a data operation.

SymptomLikely areaSafe first checks
node, uv, or gitleaks is not recognizedInstallation or PATHComplete setup. Reopen the terminal after installation.
Python environment cannot startMissing .venv/ packagesRun uv sync --locked from the repository root.
Vite or a package is missingMissing node_modules/Run npm ci with internet access.
Strict port is already in useAnother process uses 5173 or 8000Identify and stop the old app, or choose documented port variables.
Interface loads but API requests failBackend startup or proxyRead the Uvicorn error. Check /api/version and the API port.
422 responseInvalid inputRead the field and message. Correct the form or workbook row.
409 responseCurrent-state conflictReview blockers or refresh the stale view. Preview again.
Browser tests cannot start ChromeMissing browserInstall Google Chrome and rerun.
Avoid destructive shortcuts: Do not delete data/accountable.db, discard source changes, disable secret checks, or weaken tests to clear an error. Find the cause first.
11

Course completion and next steps

Your final challenge

Can you explain one saved record and one verified change without using the words “magic” or “the agent said so”?

The answer: Use this checklist. Revisit any lesson whose evidence you cannot explain.

  • Why the browser, FastAPI, and SQLite have separate jobs.
  • How a React form becomes a committed database change.
  • Why backend runtime validation remains necessary with TypeScript.
  • How active records, open deals, Trash, and app preferences differ.
  • Why a workbook is not a full backup.
  • What unit, API, browser, static, visual, and manual checks each prove.
  • How intent, specification, plan, glossary, and acceptance criteria connect.
  • How to constrain an agent's context, tools, secrets, and Git actions.
  • Why a timeout does not prove that a server operation had no effect.
  • Why review uses four passes and why 80% coverage is not 80% correctness.

For deeper study, use the official documentation. These links need internet access:

  • MDN: Learn web development for HTML, CSS, JavaScript, and HTTP.
  • TypeScript Handbook and React Learn for the frontend.
  • FastAPI tutorial and SQLAlchemy Core for the backend.
  • pytest and Playwright for testing.
  • GitHub Actions for continuous integration.

Return to the quick reference for commands and paths. Read the specification for current product behavior and the current change folder for scoped intent and plans. Keep the distinction: source documents define what to build; executed checks report what you observed.
