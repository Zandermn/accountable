01

Architecture: the system's main parts

Design puzzle

A deal shows the wrong probability. Should you change the card, the API route, the service, or the database? Without a map, every file looks possible.

The answer: Architecture assigns responsibility to each layer. Stage rules belong in shared backend services; the card presents their result.

Architecture describes the main parts of a system and their responsibilities. Accountable is a local full-stack web application with a layered backend.

Chrome └── React + TypeScript + CSS frontend/src/ ├── Views and components ├── Browser state and forms └── fetch('/api/...') │ ▼ same-origin Vite proxy FastAPI + Uvicorn backend/main.py, backend/api/ │ ▼ shared operations Python services backend/services/ │ ▼ table expressions and transactions SQLAlchemy Core + Store backend/db/ │ ▼ SQLite file data/accountable.db

This is a client-server design on one machine. It is also a layered design. Each layer has a clear job:

  • The view collects input and presents results.
  • The API translates HTTP into service calls.
  • Services validate and coordinate business operations.
  • The store controls persistence and transactions.
  • SQLite enforces low-level relational constraints.

The backend is the authority for saved state. React state is not authoritative. A pipeline card is not truly moved until the server commits and returns success.

One shared write path: Forms, board moves, workbook imports, and data commands reuse backend services. This avoids different implementations of stage probability, active links, and recovery rules.

03

Startup, requests, and shutdown

The mystery

Why does one command create two running processes, and why does closing the wrong terminal make the app stop?

The answer: The dev script coordinates Uvicorn and Vite. It starts them in order, waits for readiness, and shuts both down together.

npm run dev executes scripts/dev.mjs. This is a Node.js ES module; .mjs makes that module format explicit.

  1. Read ACCOUNTABLE_PORT and ACCOUNTABLE_API_PORT, or use 5173 and 8000.
  2. Start Uvicorn with backend.main:app on loopback.
  3. Poll GET /api/version every 100 ms until the backend responds successfully.
  4. Start Vite from the installed local package, with the frontend config and a strict frontend port.
  5. Keep both child processes alive. If one exits, stop the other.

Polling means checking repeatedly. Startup polling prevents Vite from appearing ready before the API can respond. A strict port fails instead of silently selecting a different frontend port.

Press Ctrl + C. The script handles the interrupt and stops both child processes. Closing stdin also stops them when the app runs under the browser test fixture.

A normal page load

  1. GET / returns index.html
  2. Vite serves TSX and CSS
  3. React requests /api/version
  4. Views request their data

The browser receives JavaScript modules transformed by Vite, not raw Python. FastAPI receives API requests, not requests for React component source.

05

Offline operation and local security

The mystery

The app uses HTTP but needs no internet. How can that be true—and does running locally automatically make customer data secure?

The answer: Loopback HTTP stays on your computer, and local packages and fonts remove external requests. Loopback is not authentication or encryption, so device access still matters.

After one-time setup, the app does not need internet access:

  • npm scripts start installed local tools instead of resolving packages.
  • Fonts ship in frontend/public/fonts/.
  • Chart.js and all frontend packages are bundled from local dependencies.
  • Both servers bind to loopback.
  • SQLite reads and writes a local file.

“Offline” does not mean “no network stack.” The browser still uses HTTP over the computer's loopback interface. It means no external internet service is required.

Security boundary

The current MVP has no sign-in or user accounts. Loopback binding reduces network exposure, but it is not authentication. Another process on the same computer could call the local API. Do not expose these ports to a public or shared network without a proper security design.

Local does not mean secret: SQLite and JSON backups are not encrypted by this app. Protect your Windows account, device storage, and backup copies. The app needs no .env file for its current local workflow.

Server validation protects data integrity. Database constraints add another layer. These checks are not a replacement for authentication if the app later becomes multi-user.

06

Coding-agent support files

The mystery

The MVP excludes AI features, so why does the repository contain skills, agent instructions, and an MCP configuration?

The answer: Those files support the tools used to develop the app. They do not run inside the CRM or add AI behavior for its users.

This repository belongs to an AI software-development course. Some files help coding agents; they are not application dependencies.

Path or conceptPurpose
AGENTS.mdProject guidance for coding agents: important documents, tests, and status updates.
.agents/skills/brand/Reusable brand guidance for UI work.
course/for_agents/Course-specific guidance for agents helping a student.
.mcp.jsonConfigures a Playwright Model Context Protocol server for compatible agents.
.claude/, .kimi-code/, .pi/Tool-specific or local agent settings. Some are private and ignored.

MCP (Model Context Protocol) gives a coding agent a standard way to call external tools. Here, it can expose browser automation. The npx @playwright/mcp@latest setting is for the agent tool. The Accountable app itself does not start or require MCP.

A skill is reusable agent guidance. It can change how an agent performs a task, but it does not run inside the CRM. Keep this distinction when you read the folder tree.

Current stack versus future plans

The mystery

A document mentions Supabase and Render, but there is no hosted sign-in or deployment in this app. Which statement describes the code you have now?

The answer: Current manifests and runtime source are the evidence. The stack document labels those services as future options, not installed features.

docs/TECH_STACK.md says Supabase may later provide sign-in and a hosted database, and Render may later host the application. The current source uses neither service.

TechnologyStatusBeginner meaning
SQLiteCurrentLocal file-based relational database.

This distinction matters. A course branch or a design document can mention technology that your current branch does not contain. Verify the manifests and source before you assume a service is active.

08

Check your understanding

1. Why are there two running processes?

Uvicorn serves the Python API. Vite serves and transforms the frontend and proxies API calls. The dev script coordinates their lifecycle.

2. Does offline mean HTTP is disabled?

No. Browser and backend communicate over loopback HTTP. No external internet connection is needed.

3. Is the Playwright MCP server needed by a salesperson?

No. It is an optional coding-agent integration. Playwright Test in npm test is the project's automated browser suite.

4. How can you confirm whether Supabase is active?

Check the current dependency manifests and source. The current stack document labels it as future, and the current app opens SQLite through Store.
