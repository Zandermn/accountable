Lesson 08 · Testing

Check behavior at every layer

Learn how frontend tests, backend tests, and real-browser tests catch different problems without touching your sales data.

  • About 30 minutes
  • Prerequisite: Lessons 4–7
  • Main command: npm test
The problem

Your small change works on the Dashboard. How can you know it did not break Trash recovery, workbook imports, keyboard movement, or offline startup?

Why it matters: Tests turn repeated checks into evidence. Knowing what each suite proves—and what it cannot prove—helps you trust a pass and investigate a failure correctly.

01

Tests, assertions, fixtures, and isolation

Problem to solve

You expect US$25.00 of expected revenue. Do you need to click through the app and recalculate it by hand after every change?

The answer: A test arranges known data, performs an action, and asserts the expected result. Fixtures make that check repeatable and isolated.

An automated test runs behavior and checks the result. An assertion states what must be true. If it is false, the test fails.

The basic pattern
// Arrange: prepare known data.
const deal = { value_cents: 10000, probability: 25 };

// Act: run the behavior.
const expected = deal.value_cents * deal.probability / 100;

// Assert: check the result.
expect(expected).toBe(2500);

A fixture prepares reusable test resources and cleans them up. Accountable fixtures create isolated apps, databases, backup folders, and ports.

LevelScopeStrengthLimit
UnitOne function or componentFast and specificCan miss integration problems
IntegrationSeveral real parts togetherChecks their contractMore setup and slower
End to endUser flow through the real systemClosest to actual useSlower and more moving parts

A mock or stub replaces a dependency with controlled behavior. Frontend unit tests replace fetch(). Browser tests do not mock the backend: they start the real app.

Test isolation: Passing tests must not depend on your personal database or on another test's leftovers. Accountable gives each backend or browser test temporary data resources.
02

Vitest, Testing Library, and jsdom

Problem to solve

How can you check a dialog's focus behavior hundreds of times without opening Chrome and clicking through it yourself?

The answer: Vitest runs the component in jsdom, Testing Library interacts through accessible roles and labels, and mocks control API responses.

Vitest runs frontend unit tests. React Testing Library renders components and finds elements by roles, labels, and text. jsdom supplies a DOM implementation inside Node.js. It is not a full Chrome browser.

The config is in frontend/vite.config.ts. Tests use environment: 'jsdom' and load frontend/src/test-setup.ts. Test files sit beside source files with names such as Sales.test.tsx.

Simplified frontend test
vi.stubGlobal('fetch', vi.fn(async () => ({
  ok: true,
  json: async () => board
})));

render(
  <MemoryRouter initialEntries={['/pipeline']}>
    <SalesWorkspace onBoard={true} id="" />
  </MemoryRouter>
);

fireEvent.click(await screen.findByLabelText('Move Renewal'));
expect(screen.getByRole('dialog')).toBeVisible();
  • vi.fn() creates a mock function.
  • vi.stubGlobal() replaces a browser global for the test.
  • MemoryRouter supplies test URLs without changing a real browser address.
  • screen.findBy... waits for asynchronous rendering.
  • expect() makes the assertion. jest-dom adds DOM-specific matchers.

Real frontend tests check query parameters, form errors, note-draft preservation, blocker links, backup confirmation cancellation, and recovery after a rejected board move.

Run only this suite with:

npm run test:ui
03

pytest, HTTPX, and FastAPI TestClient

Problem to solve

How can tests create, delete, and restore records without deleting anything from your actual accountable.db?

The answer: pytest fixtures create a temporary empty app and backup path. TestClient and HTTPX exercise its API without using your saved dataset.

pytest discovers and runs Python tests. HTTPX is an HTTP client library. FastAPI's TestClient uses it to call the application in the test process without opening a public network port.

The api fixture in backend/tests/conftest.py does four important things:

  1. Uses pytest's tmp_path for a unique temporary directory.
  2. Sets a temporary backup path with monkeypatch.
  3. Builds the app with seed=False, so each test starts empty.
  4. Adds X-Dataset: 1 to client headers for writes.
Simplified backend test
def test_expected_revenue(api):
    org = add(api, "organizations", name="Buyer")
    deal(api, value_cents=10000, probability=25,
         organization_id=org["id"])

    response = api.get("/api/dashboard")

    assert response.status_code == 200
    assert response.json()["totals"]["expected"] == 2500

The backend suite tests API behavior and some service calculations directly. Cases cover record rules, links, stale writes, deletion and restore, stage events, ordering, dates, totals, workbook safety, backup validation, and startup persistence.

The root pyproject.toml sets testpaths = ["backend/tests"] and puts the repository root on Python's import path.

Run only this suite with:

npm run test:api
04

Playwright Test and installed Chrome

Problem to solve

Every component and API test passes, but a real user still cannot drag a card or restart the app. Which layer can expose that gap?

The answer: Playwright drives installed Chrome through the real frontend, backend, and database. Its isolated fixture can even restart the full app.

Playwright Test controls a real browser. Accountable uses installed Google Chrome through channel: 'chrome'. End-to-end files live in e2e/.

Simplified browser test
test('opens Contacts', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('link', { name: 'Contacts', exact: true }).click();
  await expect(
    page.getByRole('heading', { name: 'Contacts', exact: true })
  ).toBeVisible();
});

Playwright auto-waits for many UI conditions. Tests use accessible locators such as role and label. This checks what a user can perceive instead of depending only on implementation details.

The custom fixture in e2e/fixture.ts:

  • Creates a temporary database and backup directory.
  • Finds free frontend and API ports.
  • Sets npm offline mode.
  • Starts npm run dev -- --stdin and waits for the API.
  • Lets a test restart the app to check persistence.
  • Stops processes and removes temporary files afterward.

The config uses one worker so browser cases do not compete for shared process resources. You do not need to start the app before running browser tests.

Run only this suite with:

npm run test:e2e

Playwright can write screenshots, traces, and failure output under test-results/. These are generated files, not source code.

05

One command, three suites

Problem to solve

If the frontend suite fails, why should you still want backend and browser results from the same run?

The answer: The runner collects evidence from all three layers and returns a nonzero code if any suite fails or cannot start. One failure does not hide the others.

npm test

The root command runs scripts/test.mjs, which runs:

  1. Vitest frontend tests
  2. pytest backend tests
  3. Playwright Chrome tests

It runs each suite even if an earlier suite fails. The final exit code is nonzero if any suite fails or cannot start. An exit code of 0 means success. Automation uses this code instead of reading colored output.

The runner gives pytest a fresh temporary base directory and cache. This avoids a Windows access problem from an old directory owned by another account. It removes that directory afterward.

PurposeCommand
All testsnpm test
One frontend test filenpm run test:ui -- src/Sales.test.tsx
One backend test filenpm run test:api -- backend/tests/test_sales.py
One browser test filenpm run test:e2e -- e2e/startup.spec.ts

Build and tests are different: A build can succeed while behavior is wrong. Tests can pass while a production bundling step fails. Run the project's required checks for the kind of change you make.
06

How to read a failing test

Problem to solve

The terminal fills with red output. Do you change the first assertion until it turns green, or is there a better investigation path?

The answer: Start with the behavior, setup, and expected-versus-received difference. Reproduce the smallest case, find the cause, then run all suites again.

  1. Find the first clear failure. Later output can be a consequence.
  2. Read the test name and file path. They identify the behavior and location.
  3. Compare expected and received values. Check the assertion diff.
  4. Check setup errors. A missing dependency or occupied port is different from a wrong result.
  5. Reproduce the smallest scope. Run that one file or test while investigating.
  6. Run all suites before completion. A local fix can affect another layer.

Do not change an assertion just to make it pass. First decide whether the source or the test is wrong according to docs/intent.md and docs/spec.md. A familiar error message can have a different cause in a new context.

A test that cannot start is not a passed test. Missing Chrome, Python, or Node dependencies must be fixed through the normal setup path.

07

Quality beyond automated tests

Problem to solve

Every test is green, but focus is hard to see and a font needs the internet. Can automation alone declare the app ready?

The answer: No. Visual, keyboard, console, offline, and cross-platform checks cover qualities that the current assertions may not observe.

Automated tests reduce risk. They do not prove that every user experience is correct. Accountable's sign-off also needs:

  • Visual checks against the brand and approved mockup.
  • Keyboard and focus checks.
  • Browser console inspection for errors.
  • Offline startup and use after setup.
  • Representative save, load, reset, import, and export operations.
  • Checks on Windows, macOS, and Linux for the full release criterion.

Regression means previously working behavior breaks after a change. Regression tests preserve known behavior. A useful test has a clear arrange, act, and assert path and uses isolated data.

08

Check your understanding

1. Why not use only Playwright tests?

Browser tests are valuable but slower and broader. Unit and API tests locate small logic failures quickly. The three levels provide complementary evidence.

2. Does jsdom prove that Chrome renders correctly?

No. jsdom supplies DOM behavior in Node.js. Playwright with installed Chrome checks the real browser.

3. Can npm test change data/accountable.db?

The suites use temporary test databases and backup paths. Browser tests also use temporary ports. The standard runner is designed not to touch your app data.

4. What does a nonzero exit code mean?

At least one suite failed or could not start. Read the output and do not report the run as passing.
