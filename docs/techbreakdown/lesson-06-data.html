Lesson 06 · Data and APIs

Follow the life of a record

Learn how CRM records connect, how API operations change them, and how Trash, workbooks, and backups protect your work.

  • About 35 minutes
  • Prerequisite: Lessons 4–5
  • Database: data/accountable.db
The problem

If you rename an organization, how do its contacts and deals find the new name? If you delete a contact by mistake, what makes a safe restore possible?

Why it matters: Data design answers both questions. IDs, relationships, revisions, and deletion metadata keep records connected and recoverable instead of relying on names or luck.

01

CRM records and relationships

Design puzzle

Why not copy the organization's name into every contact and deal? It looks simpler until the organization is renamed or deleted.

The answer: Separate records connected by stable IDs store each fact once while preserving useful links. That prevents contradictory copies.

A CRM is a Customer Relationship Management system. Accountable has four record kinds:

RecordMeaningImportant fields
OrganizationA company or other organization.Name, website, industry, notes.
ContactA person, with or without an organization.Name, Lead/Qualified/Customer status, details, optional organization.
DealA potential sale.Stage, value, probability, dates, optional organization and main contact.
ActivityA note, call, or email attached to one owner.Type, description, occurrence time, optional follow-up and done state.

A relationship connects records. An organization can have many contacts and deals. A contact can have many activities. A deal can have many activities and stage events. Each contact has at most one current organization. Each deal has at most one current organization and one main contact.

A deal must have an organization, a main contact, or both. These are three valid combinations. A deal with neither is invalid.

Organization ├── Contact │ └── Activity └── Deal ──── Main contact (optional) ├── Activity └── Stage event
Lead is not another table: A lead is a contact whose status is Lead. The Contacts view filters the same contact records by status.

The six fixed stages are New, Qualified, Proposal, Negotiation, Won, and Lost. Default probabilities are 10%, 25%, 50%, 75%, 100%, and 0%. A manual probability remains until the stage changes. A stage change applies the new stage's default.

02

Database tables and stored values

Design puzzle

Why can US$0.01 rounding, duplicate names, or a time-zone conversion corrupt a sales report or a close date?

The answer: The schema uses deliberate representations: integer cents, unique IDs, calendar dates, and UTC timestamps. Constraints reject values that break the rules.

The schema defines tables, columns, keys, and constraints. Accountable's schema version is 1. Its main definitions are in backend/db/__init__.py.

TablePurpose
organizations, contacts, deals, activitiesCurrent and deleted user records, including deletion metadata.
eventsDeal stage history for timelines and funnel calculations.
detachedOrganization-link history used during recovery.
stateSchema version, dataset ID, and data revision.
backup_confirmationsServer-issued tokens for the two-step backup deletion flow.

Most record IDs are UUID strings. A UUID is a practically unique generated identifier. IDs connect workbook rows and database records. Duplicate names are allowed; names are not identity keys.

Money, dates, and times

  • Money: nonnegative integer cents. The UI adds the US$ currency label and formats decimals.
  • Probability: a whole number from 0 to 100.
  • Calendar dates: ISO text such as 2027-01-15. Expected and actual close dates have no time component.
  • Timestamps: ISO date-time strings normalized to UTC. The browser uses local date and time for display.

UTC is Coordinated Universal Time, a common reference for saved timestamps. Keeping calendar dates separate prevents a close date from moving to another day because of a time-zone conversion.

Expected revenue

For each active open deal, expected revenue is value multiplied by probability. Accountable sums the exact cent-probability products first and then rounds the total to cents.

Deal A: 10000 cents × 25% =  2500 cents
Deal B: 20000 cents × 50% = 10000 cents
Total expected revenue     = 12500 cents = US$125.00

Won and Lost deals are closed. They do not contribute to open pipeline totals. However, they remain active outside Trash and can still block some deletions.

03

API operations and one request flow

The mystery

What actually travels across the wire when you click Save contact? Is the whole web page sent back and forth?

The answer: The browser sends a focused HTTP request with JSON. The API validates and saves it, then returns JSON that React uses to refresh the affected views.

CRUD means Create, Read, Update, and Delete. Accountable's record API uses these main patterns:

OperationMethod and path
List recordsGET /api/records/{kind}
Read one recordGET /api/records/{kind}/{id}
Create a recordPOST /api/records/{kind}
Edit fieldsPATCH /api/records/{kind}/{id}
Preview deletionGET /api/records/{kind}/{id}/delete-preview
Move to TrashDELETE /api/records/{kind}/{id}
List or restore TrashGET /api/trash, POST /api/trash/{kind}/{id}
Read or move PipelineGET /api/pipeline, POST /api/pipeline/move
Read DashboardGET /api/dashboard
Workbook operationsGET|POST /api/workbook/{mode}
Backup operations/api/backups routes
Read data versionsGET /api/version

List endpoints accept search and sort query parameters. Contacts also accept status. Example:

GET /api/records/contacts?search=amina&sort=name&direction=asc&status=Lead

Create a contact: end to end

Example HTTP request body
POST /api/records/contacts
Content-Type: application/json
X-Dataset: 1

{
  "name": "Amina Yusuf",
  "status": "Lead",
  "email": "amina@example.com",
  "organization_id": null
}
  1. React's api() helper serializes the body and adds headers.
  2. Vite proxies the request to FastAPI.
  3. The route opens store.write(x_dataset).
  4. The store checks the dataset and takes the write lock.
  5. The record service trims and validates fields, then inserts the row.
  6. The store advances the revision and commits.
  7. FastAPI returns the saved row as JSON. React refreshes affected reads.

For a failed validation, the service raises Problem. The transaction rolls back. The error handler returns a useful status and JSON details. No partial record is saved.

04

Soft deletion, Trash, and restoration

Problem to solve

You delete a contact and its notes disappear. What if you needed that history tomorrow? What if another deal still depends on the contact?

The answer: Soft deletion keeps recoverable rows, blockers protect required links, and revision checks ensure the impact you confirmed is still current.

Accountable uses soft deletion. A delete sets deletion metadata instead of immediately removing the row. Main queries hide deleted records. Trash can restore them. There is no permanent-delete action for records in Trash.

A deletion preview returns current blockers, linked records that will be cleared, and activities that will move with the record. The final delete includes the preview revision. If data changed, the server rejects the stale action.

RecordImportant rule
ContactAn active deal that uses it as main contact blocks deletion. Its active activities move with it.
OrganizationAn active deal with no main contact blocks deletion. Otherwise, active contacts and deals stay but lose that organization link.
DealIts active activities move with it. Restore requires at least one active organization or main contact.
ActivityIt can move independently or with its owner. Individual restore requires an active owner.

Recovery preserves choices. For example, restoring a contact can restore its previous active organization or restore it as an individual. Restoring an organization reattaches only eligible former links. A newer link or an explicit choice to stay independent takes priority.

Activities that moved with a parent have deletion-operation metadata. This prevents a parent restore from reviving an activity that the user deleted separately.

05

Spreadsheet import and export

Problem to solve

An import has 100 valid rows and one bad link. Should 100 records change before the error appears? What if the database changed after the preview?

The answer: Validation and one transaction prevent partial imports. A preview token detects a changed workbook or dataset and forces a fresh review.

An Accountable workbook has up to three named sheets: Organizations, Contacts, and Deals. Download the template from Data to get the required headers.

  1. Upload and preview
  2. Review adds and updates
  3. Apply one transaction

A blank ID creates a record with a generated ID. A known active ID updates that record. A new supplied ID can link rows across sheets and is retained. Matching uses IDs only, never duplicate names.

The parser checks sheet names, headers, cell types, duplicate IDs, formulas, values, and links. Dollar values convert to integer cents. Dates must be Excel dates or YYYY-MM-DD. Blank optional cells clear fields during an update.

The preview token is a SHA-256 hash of the workbook bytes, dataset, and revision. A hash produces a fixed-length fingerprint. If the file or data changes before Apply, the token no longer matches. The user must preview again.

Export includes active organizations, contacts, and deals. It does not include activities, Trash, stage history, follow-up state, or board order.

A workbook is not a full backup: Use npm run save for complete recovery. Use a workbook to exchange the three main active record types.
06

Full local backups and replacement

Problem to solve

You are about to load an old backup or reset the dataset. What happens to the records currently on screen if something goes wrong halfway?

The answer: The app saves current data first, validates the snapshot, writes files atomically, and replaces tables in one transaction. A failed backup blocks replacement.

npm run save snapshots all application data tables into a versioned JSON document. Backups go to data/backups/ by default. A backup includes active records, Trash, events, recovery links, follow-up state, and board positions.

Simplified backup document
{
  "format": 1,
  "id": "backup-...",
  "created_at": "...",
  "checksum": "SHA-256 of the data",
  "data": {
    "organizations": [],
    "contacts": [],
    "deals": [],
    "activities": [],
    "events": [],
    "detached": []
  }
}

The service writes a temporary file, flushes it to disk, and publishes it with an atomic file replacement. The checksum and schema checks detect an invalid or damaged backup. The checksum is not encryption. Backup JSON can contain readable business data.

npm run load -- <backup-id> validates the selected backup, saves the current data first, then replaces all application tables in one writer transaction. If automatic backup fails, replacement does not proceed. A successful load advances the dataset ID.

npm run seed follows the same safety pattern before replacing current data with samples. It asks you to type yes. Press Enter to cancel.

Deleting a backup is permanent and separate from Trash. The Data view requires two confirmations. The backend binds the confirmation token to the selected backup ID.

Protect business data: The database and backups are local and ignored by Git. Keep them in access-controlled storage. Do not send real customer backups to a public repository or an untrusted service.
07

Check your understanding

1. What is the difference between active and open?

Active means outside Trash. Open means a deal is in New, Qualified, Proposal, or Negotiation. A Won deal outside Trash is active but not open.

2. Why does a deletion preview include a revision?

It proves which data state the user reviewed. If records changed before confirmation, the server rejects the old preview instead of applying a deletion to unseen effects.

3. Why can an export not restore the whole app?

It excludes activities, Trash, stage events, follow-up completion, recovery metadata, and board order. A full JSON backup includes those parts.

4. Why match workbook rows by ID instead of name?

Duplicate names are valid. IDs provide stable identity and unambiguous cross-sheet links.
