Lesson 09 · Specification-driven development

Define the right change before writing code

Turn a user outcome into shared language, current product behavior, a bounded plan, and observable acceptance checks.

  • About 45 minutes
  • Prerequisite: Lessons 1–8
  • Main source: docs/spec.md
The problem

Two developers hear “make deletion safer.” One adds a confirmation. Another adds Trash. A third blocks every deletion. Which one is correct?

Why it matters: A short request does not define the product. Intent, existing behavior, edge cases, and acceptance checks turn opinion into a testable agreement. This is essential when a coding agent can produce plausible code very quickly.

In this lesson

  1. Sources of truth
  2. Intent and scope
  3. Domain language and invariants
  4. Behavior and failure cases
  5. Implementation plans
  6. Acceptance and traceability

01

Use the right source of truth

The mystery

A mockup shows one layout, an old note describes another, and the app behaves in a third way. Which one should a change follow?

The answer: Each document has a defined job. The current specification defines product behavior; a change's intent and plan define the new work. Mockups and old status entries supply evidence, not automatic permission to change scope.

SourceQuestion it answersHow to use it
docs/spec.mdWhat does the whole product do now?Read first. Preserve behavior outside the requested change.
docs/changes/<branch>/intent.mdWhy this change, for whom, and within what boundaries?Read only the current change's folder. Resolve missing outcomes and exclusions here.
docs/changes/<branch>/plan.mdHow will the change be implemented and proved?Connect phases to files, risks, and completion checks.
docs/Standers.mdWhat makes code readable and maintainable here?Apply during design, implementation, and review.
GLOSSARY.mdWhat do business words mean?Use the same terms in UI, code, documents, and tests.
docs/TECH_STACK.mdWhich technologies and library choices are agreed?Check before adding a tool or dependency.
docs/STATUS.mdHow do I run the project, and what was verified?Use current commands; update it after a finished piece of work.
Do not invent missing requirements: If the documents do not answer a product question, ask the user or record an explicit assumption. Code is not a substitute for a product decision.

The approved visual reference is docs/mockups/06-deal-workspace.html. It guides appearance. The specification still controls behavior, including later additions such as the shared theme control.

02

Start with intent and bounded scope

Problem to solve

A user asks for “a better Dashboard.” Should an agent redesign every screen and add reporting while it is there?

The answer: No. Define the user outcome, the affected workflows, and what must not change. A small, explicit scope makes implementation and review possible.

A useful intent describes the problem without jumping straight to a framework. It records:

  • User and outcome: Who needs to do what, and why?
  • Current problem: What prevents that outcome now?
  • In scope: Which views, operations, and data are affected?
  • Out of scope: Which tempting additions are excluded?
  • Constraints: Offline use, local data, accessibility, brand, technology, and compatibility.
  • Completion evidence: What must another person be able to observe?
A bounded request, not a real pending feature
Outcome: A salesperson can identify overdue follow-ups in either theme.
In scope: Follow-up labels and contrast on Dashboard.
Preserve: Dates, completion behavior, all other routes, and saved data.
Exclude: A new reporting system and mobile layout.
Evidence: Unit checks plus keyboard and visual checks in both themes.

Notice what this request does not do: it does not prescribe a new library, and it does not allow unrelated redesign. Technical choices come after the outcome and constraints are clear.

03

Use domain language and invariants

Design puzzle

A Won deal is outside Trash. Is it active? Is it open? Can it block deletion of its main contact?

The answer: It is active but not open, and it can block deletion. Precise domain definitions prevent a boolean name or an assumption from changing business behavior.

The domain is the business area the software models. A shared glossary gives its words exact meanings. An invariant is a rule that must remain true after every valid operation.

Example invariantWhere it is enforced
An active deal has an active organization, an active main contact, or both.Shared service validation and database constraints.
An activity has exactly one owner: a contact or a deal.Record service and a database check constraint.
A stage change applies the destination default probability and creates one event.Shared record and sales operations, checked by backend and browser tests.
Only active, open deals contribute to open pipeline totals.Backend sales calculations.

Write rules with the same words everywhere. Do not call a contact a “lead record” in one module and a “prospect” in another. A lead is a contact with Lead status. Consistent names make searches, reviews, and agent prompts more reliable.

Try it: Find the definitions of active and open in docs/spec.md. Then find their effects in backend/services/sales.py and backend/services/trash.py. The same terms control different operations.
04

Describe behavior, including failure and time

The problem

The requirement says “save the selected theme.” What should happen if the response never arrives, the server saved before timing out, or the user retries?

The answer: The requirement must cover uncertain completion, visible recovery, and newer-versus-older responses. Happy-path text alone leaves the most difficult behavior undefined.

For each operation, consider more than the normal click:

Before

What input, permissions, links, revisions, and initial state are required?

Success

What changes atomically? What response, refresh, history, and focus result?

Failure

What remains unchanged? What message, retry, reload, or recovery is available?

Also ask what happens when an action repeats, arrives late, conflicts with newer data, or follows a restart. Accountable uses dataset and record revisions for stale-state checks. Its theme code uses deadlines and stale-response protection because an aborted browser wait does not prove that the server did no work.

State the preservation rule: “Keep the last saved view” or “preserve the draft” is more useful than “handle errors.” It tells implementation and tests what must survive.
05

Turn behavior into an implementation plan

Design puzzle

Should a plan list “edit React, edit Python, run tests,” or should another developer be able to carry it out without guessing?

The answer: A useful plan names behavior, existing seams, risks, and proof. File names help only when they make the responsibility clear.

A plan is a design and verification tool, not a prediction that must survive unchanged. Include:

  1. Context: The user outcome and current gap.
  2. Approach: The selected design and its main tradeoff. Reuse existing modules and libraries.
  3. Key changes: Group by behavior or subsystem. Name the functions or modules that own each rule.
  4. Data and compatibility: Schema versions, migrations, API contracts, backups, and existing saved state.
  5. Verification: Tests for success, boundaries, failure, regression, accessibility, and the real user workflow.
  6. Assumptions: Decisions made without user input and why the default is reasonable.

Do not abstract before a second real use requires it. Do not add a dependency before checking package.json, frontend/package.json, and pyproject.toml. Keep functions short and focused, and name them after domain behavior.

06

Make acceptance observable and traceable

The problem

Is “Pipeline works well” a useful acceptance criterion? What would two reviewers check?

The answer: No. Use a known starting state, an action, and an observable result. Include negative and stale cases so the check can fail for a useful reason.

An acceptance criterion is an observable condition that must hold for the change to be accepted. A trace connects requirement → implementation → verification.

RequirementImplementation pathEvidence
A stage change uses the destination default and adds one event.Move dialog → API route → shared sales/record service → events table.Backend assertions for probability and event count; browser check of timeline and totals.
A same-stage reorder preserves probability and adds no event.Pipeline placement → saved positions in one transaction.Backend regression test and saved order after refresh.
A stale delete preview cannot remove a newly changed relationship.Preview revision → final delete revision check.409 Conflict test and unchanged records.

Good checks use public behavior and accessible controls. Avoid assertions tied to private variable names or irrelevant markup. Coverage can show unexecuted code, but a high percentage does not prove that requirements were checked.

07

Follow one change from start to finish

Your challenge

Can you keep product decisions, implementation decisions, and verification evidence separate without losing their connections?

The answer: Use a repeatable workflow and update the source documents when behavior changes.

  1. Understand intent
  2. Specify behavior
  3. Plan and implement
  4. Review and verify
  5. Record and improve
  1. Read AGENTS.md and docs/spec.md.
  2. Create or read only docs/changes/<current-branch>/ for intent and plan.
  3. Clarify domain terms, invariants, exclusions, and failure behavior.
  4. Inspect current source and tests before choosing edits.
  5. Implement the smallest coherent change that meets the intent.
  6. Run focused checks while working; run npm run check before completion.
  7. Review bugs, security, specification and plan compliance, and project standards separately.
  8. Update the specification when current product behavior changes. Update docs/STATUS.md with finished work and actual evidence.
  9. At Deploy, follow docs/IMPROVE.md after review fixes and before merge.
Unspecified code is a review finding: The review policy says to flag code that docs/spec.md does not describe. “The agent added it” is not a reason to keep it.
08

Check your understanding

1. What is the difference between the product specification and a change plan?

The specification describes current whole-product behavior. A change plan describes how one bounded change will be implemented and verified. After the behavior changes, the specification must be updated too.

2. Why is “add validation” incomplete?

It does not name the valid values, the operation, the error response, the preserved state, or the test evidence. A useful requirement makes those points observable.

3. Why should a stage change have a negative reorder test?

The negative case proves that reordering does not create a stage event or reset probability. Testing only transitions would miss that distinction.

4. Can an agent make a product decision when the documents are silent?

It can propose options or state an assumption, but the user owns unresolved product scope. Silent invention creates unreviewable behavior.
