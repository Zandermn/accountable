Lesson 11 · Debugging and delivery

Finish with causes, review, and proof

Reproduce failures, test the fix, inspect the change from four viewpoints, and record exactly what is ready and what remains unverified.

  • About 45 minutes
  • Prerequisite: Lessons 8–10
  • Main command: npm run check
The problem

The code looks reasonable, the tests pass, and the agent wants to stop. What could still make the change unsafe to merge?

Why it matters: The wrong requirement, an unseen security effect, a stale response, or an untested platform can remain after green tests. Delivery is a decision supported by several kinds of evidence.

01

Diagnose before fixing

The problem

The browser shows “request failed.” Should you increase every timeout, retry every request, or delete the local database?

The answer: Not without evidence. A timeout, validation response, stale revision, unavailable server, and wrong URL need different treatment. Find the observed failure and its cause first.

A diagnosis connects a reproducible symptom to a mechanism in the system. Use this loop:

  1. State the expected behavior. Cite the specification or current change.
  2. Capture the actual behavior. Record the route, input, status, response, console message, and relevant initial state.
  3. Make it repeatable. Find the smallest reliable sequence. Note whether it is intermittent.
  4. Bound the failure. Does it affect one component, one API, one theme, one OS, or every path?
  5. Form a hypothesis. Name the suspected mechanism and what observation would disprove it.
  6. Test the hypothesis. Inspect the responsible code or run a focused experiment. Do not change several variables at once.
  7. Fix the cause. Keep the change at the owning layer and preserve unrelated behavior.
  8. Verify broadly. Rerun the original scenario and the complete required checks.
ObservationUseful next question
No frontend response at allIs Vite running on the expected port, and did startup complete?
Frontend loads but every API request failsDid Uvicorn become ready, and does the Vite proxy target the correct API port?
422Which field or workbook cell is invalid under the current rules?
409Did a revision, dataset, blocker, or relationship change after the view or preview?
Only Chrome fails while jsdom passesWhich real rendering, focus, timing, font, or integration behavior is missing from the unit environment?
Do not clear obstacles destructively: Do not delete data/accountable.db, disable a check, weaken an assertion, or discard unrelated edits to make a failure disappear.
02

Case study: an uncertain theme save

The mystery

The browser stops waiting for a theme save and restores the previous color. Does that prove the server did not save the new choice?

The answer: No. Aborting the browser's wait does not cancel work that the server already completed. The browser now has an uncertain result, not a guaranteed rollback.

The current implementation in frontend/src/theme.tsx shows several advanced ideas:

  • A three-second startup deadline lets the workspace open in light mode when the preference read stalls.
  • An AbortController and attempt cleanup prevent an old read from replacing a newer retry.
  • A five-second save deadline prevents an indefinite busy state.
  • The control cannot start another save while one is pending.
  • On an unconfirmed save, the interface restores the previous mode and tells the user to reload or retry.

After a timeout, the saved value and displayed value can differ. e2e/theme.spec.ts checks that a later reload reads the value the server actually saved. This is more honest than claiming that the write was undone.

Reasoning about request states
Response confirmed     → use the confirmed saved state.
Request clearly failed → show failure and preserve recovery options.
Response timed out     → completion is uncertain; reload to reconcile.
Older response arrives → it must not replace a newer attempt.

The general lesson applies to deletes, imports, payments, deployments, and any external action: a lost response is not evidence of no effect.

03

Prove that a regression test can catch the defect

Design puzzle

A new test passes beside the fix. How do you know it tests the defect rather than passing on both the old and new code?

The answer: Run the test against the unfixed behavior and watch it fail for the intended reason. Then apply the fix and watch the same test pass.

A regression test preserves a behavior that previously broke. The theme work followed the useful sequence:

  1. Reproduce stalled response
  2. See regression test fail
  3. Fix request handling
  4. See same test pass
  5. Run full check

If you cannot safely check out the old code, use a temporary controlled experiment or explain that you did not observe the pre-fix failure. Never claim “fails before, passes after” without running both sides.

A strong regression test uses the public behavior a user or client observes. It does not overfit private variable names. Include the boundary: old responses versus new attempts, stage transition versus reorder, or parent deletion versus separately deleted activity.

04

Keep the implementation maintainable

Design puzzle

A fix works but adds three booleans, a duplicate rule, and a generic helper used once. Is the work finished?

The answer: Not yet. The change must also be readable and fit its module. Correct behavior with unclear ownership creates the next defect.

Apply the project standards during the final edit:

  • Use expressive domain names such as active, open, revision, and dataset.
  • Give each function one purpose and keep it short enough to reason about.
  • Reuse the existing service boundary rather than copying a rule into a route or component.
  • Do not build a general abstraction for one speculative use.
  • Delete unused code instead of leaving commented-out alternatives.
  • Use short comments for why when the code cannot express it; remove comments that describe old behavior.
  • Test behavior and contracts, not irrelevant implementation details.

Also check nearby documentation and types. A schema version, command, route, theme capability, or file move can make old lessons and status statements false.

05

Make four separate review passes

The problem

Why not read the diff once and look for anything suspicious?

The answer: One mixed pass favors obvious style issues and can miss requirements or security. Separate passes give each kind of risk full attention.

docs/REVIEW.md requires four passes over every change:

1 · Bugs

Does the code do what it means to do, including invalid input, conflicts, repeated actions, late responses, and rollback?

2 · Security

Are secrets or personal data exposed? Can a caller do something it should not? Are local-only assumptions still valid?

3 · Spec and plan

Is every requested behavior present, with nothing missing and nothing extra? Flag code the product specification does not describe.

4 · Standards

Are naming, function size, module boundaries, comments, and test design consistent with the repository?

An Important finding blocks merge: it breaks expected behavior, leaks data, or breaks a rule in AGENTS.md. A Nit is a small non-blocking point such as style or naming; report at most five.

For each finding, give the file and line, the trigger, the effect, and the relevant requirement. State when a category has no findings and identify checks you could not complete. “Looks good” without a reviewed range or scope is weak evidence.

The configured reviewer agent is read-only. It reviews the requested branch and base, normally the merge base with local main, and does not silently include local edits or change the code.

06

Inspect the real user experience

The problem

All tests pass, but dark-mode text is hard to read, a dialog loses focus, and a chart needs a font from the internet. Which gate catches these?

The answer: Real-browser visual, keyboard, console, network, and accessibility inspection. Unit tests cannot observe every rendered quality.

For UI work, compare the running app with the specification, .agents/skills/brand/SKILL.md, and the approved mockup. Check every main route and representative detail states in both light and dark modes.

  • Wait for data and fonts before screenshots; inspect the screenshots rather than only creating them.
  • Check text and chart contrast at the sizes used. WCAG AA targets are 4.5:1 for normal text and 3:1 for large text.
  • Use only the keyboard for navigation, forms, dialogs, filters, and Pipeline movement.
  • Check visible focus, focus containment, and focus return after a dialog closes.
  • Ensure Late and Overdue use text or symbols as well as color.
  • Inspect the browser console and external requests. The app must work offline after setup.
  • Restore the original saved theme and avoid unrelated sales-data writes during inspection.

The configured ui-check agent performs a read-only browser pass with Playwright MCP and saves generated screenshots in .playwright-mcp/. Its report must include unreachable routes and other coverage gaps.

07

Understand the quality gates

The mystery

Why can CI pass while the complete local delivery check is not finished?

The answer: GitHub Actions runs the quick suite on Ubuntu. It skips Playwright. The full local command adds real-Chrome end-to-end tests.

GateWhat it runsWhat it does not prove
npm run formatPrettier and Ruff formatting.Correct behavior, lint, types, secrets, or tests.
npm run check:quickFormat checks, ESLint, Ruff lint, TypeScript, ty, Gitleaks, Vitest, and pytest.Real-Chrome end-to-end behavior.
npm run checkAll quick checks plus Playwright through npm test.Every OS, every visual quality, or every unexplored user action.
CI on branch pushCheckout, pinned-checksum Gitleaks install and scan, locked setup on Ubuntu, then check:quick.Windows, macOS, and Chrome coverage.

Vitest and pytest each require at least 80% line coverage of application code. A suite below its threshold fails. A suite above it can still miss a critical assertion.

Local hooks

lefthook.yml formats staged frontend and Python files before a commit, stages formatting fixes, then runs lint, type, and staged-secret checks. It deliberately skips the test suites. The Codex Stop hook runs npm run check before the turn ends; its second stop attempt can allow the turn to end after a failure, so the final report must still state the actual result.

npm test runs Vitest, pytest, and Playwright even if an earlier suite fails. The final exit code is nonzero if any suite fails or cannot start. Do not stop after the first red line; use all available evidence.

08

Record delivery evidence and improve the system

Your final challenge

What should another developer be able to learn without rerunning your entire session?

The answer: What changed, why, which checks passed, which environments were covered, and what remains. The repository should also become less likely to repeat the same mistake.

Before reporting completion:

  1. Inspect the final diff and git status. Remove only artifacts your own run created and the task does not need.
  2. Confirm that comments, documentation, and the course no longer describe old behavior.
  3. Run npm run check from the repository root for a code change.
  4. Exercise the original user scenario end to end with real calls. A successful import or type check is not enough.
  5. Record finished work and verification in docs/STATUS.md, including OS and tool coverage when relevant.
  6. State unresolved gaps and unrelated failures plainly. Do not mark partial work complete.

At Deploy, after review fixes and before merge, follow docs/IMPROVE.md. Look for other paths with the same failure. If a mistake happened twice, add an automated check and prove it catches the original failure. If automation is not suitable, correct project guidance or propose a standards change. Remove outdated guidance and improve the checklist last.

The delivery principle: “Done” means the requested behavior is implemented, the required evidence passes on the deliverable, and remaining limits are visible. It does not mean the agent reached the end of its reply.
09

Check your understanding

1. Why does a timed-out request need a reload or reconciliation?

The server may have completed the operation before the response was lost. Reloading reads the authoritative saved state instead of guessing.

2. What proves a regression test is useful?

It fails on the unfixed behavior for the intended reason and passes after the fix, then remains part of the normal suite.

3. Why does local npm run check still matter after CI passes?

CI uses the quick checks on Ubuntu and skips Playwright. The full local command adds installed-Chrome browser tests on the current machine.

4. Does 80% line coverage prove 80% of behavior is correct?

No. Coverage reports executed lines. Assertions, requirement selection, failure cases, visual checks, and real workflows determine the value of that execution.
