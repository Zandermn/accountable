Use the whole stack yourself

Run Accountable, observe real API calls, make and recover a change, save a backup, and verify the project.

  • About 35 minutes
  • Prerequisite: Lessons 1–8
  • Uses the real local app
Your challenge

Could you prove where a record goes after Save, recover it after deletion, and verify the app without watching another person do it first?

Why it matters: This lesson turns explanations into your own evidence. You will connect each visible action to an HTTP request, a saved change, and an automated check.

01

Prepare and protect your data

Problem to solve

You want to experiment with deletion and recovery. How can you learn with real actions without gambling with records you need?

The answer: Check the environment and save a full backup first. The exercises then use ordinary, reversible record actions and clearly avoid replacement commands.

This lesson makes changes to your local sample dataset. It uses normal app actions. If your database contains records you need, save a full backup first.

  1. Open a terminal in the repository root.
  2. Check the installed tools:
node --version
uv --version

Node.js must be 24 or later. Node.js 26 is the target. uv manages the required Python 3.12 environment. Install Google Chrome before browser tests.

If you have not completed setup, run these commands with internet access:

uv python install 3.12
uv sync --locked
npm ci

Optional but recommended before data exercises:

npm run save

Write down the printed backup ID and path. The save command can run while the app is open because it uses a consistent writer transaction.

Do not practice load or reset on needed data: This lesson does not ask you to run npm run load or npm run seed. Both replace the full current dataset after an automatic backup.
02

Start both servers

Problem to solve

Why does the development script wait for /api/version before it starts Vite instead of showing the browser URL immediately?

The answer: The wait prevents a misleading ready state: when the URL appears, both the interface and its API can respond.

npm run dev

Watch the terminal. Uvicorn starts first. The script waits for /api/version, then starts Vite. Open the printed local URL, normally http://127.0.0.1:5173.

Checkpoint: The Dashboard shows sales figures, charts, follow-ups, recent activity, and an embedded pipeline. The left navigation opens Organizations, Contacts, Deals, Pipeline, Trash, and Data.

Keep this terminal open. In a second terminal, you can run read-only commands or npm run save from the same repository root.

03

Inspect frontend and API traffic

Your investigation

Can you see the conversation behind the Dashboard instead of taking its figures on trust?

The answer: Chrome's Network panel exposes the actual API requests and JSON. You can compare those values with the charts and totals on screen.

  1. In Chrome, press F12 to open Developer Tools.
  2. Open the Network panel and choose Fetch/XHR.
  3. Reload the page.
  4. Select the version request. Inspect its URL and JSON response.
  5. Select dashboard and pipeline. Compare their JSON with what you see.
  6. Open the Sources panel and find src/main.tsx or another frontend module. Vite makes development source available for debugging.
ObservationWhat it proves
/api/version returns dataset and revisionThe backend is running and the frontend can read its current data version.
/api/dashboard contains months, totals, funnel, followups, recentThe backend calculates report data; React turns it into visual panels.
Font and module requests use the local originThe running app uses local assets rather than an external content network.

Open the Console panel. Try a harmless calculation:

Browser console
const valueCents = 12500;
const probability = 25;
const expectedCents = valueCents * probability / 100;
console.log(expectedCents); // 3125

This JavaScript runs only in your browser console. It does not change application state or the database.

04

Create, inspect, delete, and restore a record

Your investigation

A record appears on screen. How can you prove it is really saved—and then prove Trash is recovery, not permanent deletion?

The answer: Inspect the POST, refresh the browser, delete through the impact dialog, and restore from Trash. Each step tests a different part of the persistence path.

  1. Open Organizations and select Add organization.
  2. Set Name to Learning Example. Set Industry to Education. Save.
  3. Search for learning. The search is case-insensitive.
  4. In Network, inspect the POST request to /api/records/organizations. Look at the JSON body and saved response.
  5. Refresh the browser. The organization remains because SQLite saved it.
  6. Select Delete for Learning Example. Read the impact dialog and confirm if it has no blockers.
  7. Open Trash. Find the organization and select Restore.
  8. Return to Organizations and search for it again.
Checkpoint: You used React forms, a JSON POST, backend validation, a committed transaction, a soft delete, and a restore operation. Refresh did not clear the saved record.

If you created deals or contacts linked to this organization, deletion behavior can differ. Read the dialog. Do not bypass a blocker for the sake of the exercise.

05

Follow a pipeline change

Your investigation

A card appears in a new column. Did anything else change, or was the movement only visual?

The answer: Inspect the probability, totals, timeline, and move request. A stage change has business effects; a same-stage reorder changes position only.

Choose a sample deal that you can identify. A card named “Renewal” is only an example; use any available open deal.

  1. Note its current stage and probability.
  2. Select Move on the card. Choose a different open stage and a position. Submit.
  3. Observe the stage's default probability and updated column totals.
  4. Open the deal. Find a new stage event in its timeline.
  5. In Network, inspect the POST body for /api/pipeline/move. Identify id, stage, before, and revision.
  6. Move the card back if you want to restore its stage. The app records both transitions and applies the destination defaults.

Reorder a card within its current column. Its probability does not change and no stage event is created. The backend saves its position.

Expected result: A stage move changes probability and history. A same-stage reorder changes only position. The same backend service handles form edits and imports, so those paths apply the same stage rules.
06

Export a workbook and save a full backup

Problem to solve

You have an Excel export. Does that file contain everything needed to restore Trash, notes, follow-ups, stage history, and board order?

The answer: No. Comparing the workbook with a full JSON backup shows why exchange and recovery need different formats.

Workbook exchange

  1. Open Data.
  2. Select Download template and inspect the three sheet names in a spreadsheet program.
  3. Select Export workbook. Open the export and compare its IDs and rows with the app.

You do not need to import the file for this lesson. Preview is safe because it rolls back its trial changes. Apply commits only after validation and a matching token.

Complete backup

In a second terminal at the repository root, run:

npm run save

Record the new ID. Find the JSON file in data/backups/. You can open it in a text editor, but do not modify it. Its checksum would no longer match the changed data.

ArtifactContainsMain use
Workbook .xlsxActive organizations, contacts, and dealsSpreadsheet exchange
Backup .jsonAll application data and recovery stateFull local recovery
Database .dbLive SQLite tablesNormal persistent operation
07

Run verification

Your investigation

Can you show that your source builds and all three layers pass without using or resetting the data you just changed?

The answer: Run the build and combined test command. The test fixtures start isolated apps with temporary databases, backups, and ports.

Return to the app terminal and press Ctrl + C. This stops both servers. Playwright will start its own isolated app.

npm run build
npm test

The build checks TypeScript and writes frontend/dist/. The test command runs Vitest, pytest, and Playwright in order. Every suite runs even if an earlier suite fails. The final exit code must be 0 for a passing run.

Checkpoint: Identify each suite in the output. Confirm that all three completed. Read the total results and final command status. Do not call the run successful if a suite could not start.

The tests use temporary databases and backups. They do not reset the Learning Example organization or the sample board changes in your normal database.

08

Troubleshoot common problems

Problem to solve

The app will not start. Is deleting the database a sensible first step, or can the error message point you to a safer cause?

The answer: Match the symptom to the tool or layer. Check dependencies, ports, API readiness, and response statuses before you consider any data operation.

SymptomLikely areaSafe first checks
node or uv is not recognizedTool installation or PATHComplete the setup guide. Reopen the terminal after installation.
Python environment cannot startMissing .venv/ packagesRun uv sync --locked from the repository root.
Vite or a package is missingMissing node_modules/Run npm ci with internet access.
Strict port is already in useAnother process uses 5173 or 8000Identify the existing process. Stop the old app or choose documented port environment variables.
Interface loads but API requests failBackend startup or proxyRead the Uvicorn terminal error. Check /api/version and the API port.
422 responseInvalid inputRead the field and message. Correct the form or workbook row.
409 responseCurrent data conflicts with the actionReview blockers or refresh the stale view. Preview the operation again.
Browser tests cannot start ChromeMissing browserInstall Google Chrome and rerun. The config uses installed Chrome.
Avoid destructive shortcuts: Do not delete data/accountable.db, discard source changes, or disable tests to clear an error. Find the cause first. Use a full backup for intentional recovery.
09

Course completion and next steps

Your final challenge

Can you explain the journey of one saved record to another person without using the word “magic”?

The answer: Use the checklist to test your mental model. If a step is unclear, revisit its lesson; if you can explain it, you are ready for the official tool documentation.

You have a useful mental model when you can explain these points without looking:

  • Why the browser, FastAPI, and SQLite have separate jobs.
  • How a React form becomes a committed database change.
  • Why backend validation is necessary even with TypeScript.
  • How active records, open deals, and Trash differ.
  • Why a workbook is not a full backup.
  • What Vitest, pytest, and Playwright each verify.

For deeper study, use the official documentation. These links need internet access:

  • MDN: Learn web development for HTML, CSS, JavaScript, and HTTP.
  • TypeScript Handbook for static types.
  • React Learn for components, state, and effects.
  • FastAPI tutorial for routes and requests.
  • SQLAlchemy Core for tables, expressions, and connections.
  • pytest getting started and Playwright introduction for testing.

Return to the quick reference whenever you need a command, file path, API route, or term. To learn the product requirements, read the intent and then the specification.
